# AI Receptionist Demo Set

Working demo websites + AI receptionist chatbots, built as portfolio pieces
for freelance gig work (Upwork / Fiverr / Contra profiles, direct outreach)
and for resumes. Every business in this set is fictional.

## The set

| Demo | Business type | File |

## How a demo works (the code, in plain English)

Each demo is **one self-contained HTML file**: no framework, no build step,
no backend, no third-party scripts. That is deliberate — it hosts free
anywhere static, loads fast, and never goes down during a pitch.

Inside each file:

1. **The page** — a small-business website: services, hours, team, reviews.
2. **The chat widget** — bottom-right bubble opening a chat panel.
3. **The knowledge base (KB)** — a list of question/answer pairs in the
   business's own voice. The bot matches typed questions against it with
   phrase/keyword scoring, answers up to three questions at once, and never
   invents an answer it doesn't have (it takes a message instead).
- **Everyday language** — greetings, thanks, typos, text-speak, open-now
  questions, and bare urgent words are handled before the knowledge base,
  so ordinary messages never hit the fallback.
4. **Lead capture** — a 3-step state machine (name → phone → need). In the
   demo, leads appear in the on-page "What the owner sees" panel.
5. **Hours engine** — open/closed is computed from the business's hours,
   with an after-hours mode and a demo toggle for pitches.
6. **The LLM swap point** — one function, `getAnswer()`. In a paid client
   build this calls a server endpoint instead of the rule-based matcher.
   Everything else carries over unchanged.

## How to set one up for a real business (replicable process)

1. **Intake** — a short form + the client's existing site/Facebook page:
   services, prices ("starting at" only), hours, address, phone, staff
   names, and the 20–30 questions customers actually ask.
2. **One config block** — all of that goes into a single business dict in
   `build_demos.py` (copy any existing one: `DENTAL`, `AUTO`, `SALON`, or `CAFE`).
   You never touch the shared template or the chat engine.
3. **Generate** — run `python3 build_demos.py`. It writes one standalone
   HTML file per business, plus `index.html`.
4. **Verify** — run `node verify_all.mjs`. It checks the chatbot answers
   sample questions correctly, the hours logic, and the safety checks
   (fictional banner, builder credit, 555 phone numbers, message cap).
5. **Host free** — GitHub Pages, Netlify, or Cloudflare Pages. That link
   fills the `[demo link]` placeholder in the gig profiles.
6. **For a paying client, swap the demo parts for production parts:**
   - Remove the on-page "What the owner sees" panel; send leads to the
     owner's email and/or a Google Sheet instead.
   - Keep the KB to public, customer-facing info only.
   - If the client wants LLM answers: server-side endpoint (API key never
     in the page), KB-grounded prompt, no tool/data access, and the
     take-a-message fallback stays in place.

## Safety notes (from review, 2026-10-24)

- Rule-based demos have no model to prompt-inject and no backend to
  attack; a visitor can only get back public page content. Visitor input
  is inserted as plain text, never HTML.
- Chat sessions are capped at the last 200 messages; chat input is capped
  at 500 characters; one repeating timer; listeners attached once.
- All four demos are generated from configs in this file; there is no
  hand-built outlier left to drift.

## Publishing

The `chatbot-demos-site/` folder is generated by `build_demos.py` on every run (all four generated demos and a site index with fixed links). Never edit it by hand — edit the source and re-run the build.

## Files

- `build_demos.py` — shared template + business configs + generator.
- `verify_all.mjs` — chatbot/hours/safety checks for every demo.
- `replicate_test.py` — proof that a new business can be added by copying
  a config: it clones the café config under a new name, generates a demo,
  and verifies it.
